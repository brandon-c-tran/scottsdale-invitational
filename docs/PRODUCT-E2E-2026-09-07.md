# Field Day: product E2E review

September 7, 2026 · Commissioner, player and TV

For the larger product changes prompted by this audit, start with [Product direction](PRODUCT-DIRECTION-2026-09-07.md): coordinated preparation, delegated event operation, personal participation, shared results and a complete finale workflow.

**Recommendation: keep the current direction and consolidate the system underneath it.** Direct chips, the full leaderboard, player cards and the restored draw/draft moments are working. The most consequential friction comes from inconsistent activity selection, incomplete save/recovery flows, stale commissioner edits and an unclear poker counting transition. These should drive the next design and refactor pass.

Player and commissioner journeys are mobile-first; TV remains the shared room display. Prioritize clear next actions, usable touch targets and continuity between those roles.

**22 findings: 7 P1, 13 P2, 2 P3.** P1 means a blocked core task, untrustworthy shared state or an established privacy promise not being met; P2 is material friction/inconsistency; P3 is contained polish. These are product priorities, not security CVSS ratings. No new blank-screen crash was encountered in the browser walkthroughs. The announcement regression did not recur.

Open the [interactive findings board](product-audit-2026-09-07.html) to filter by role, priority and evidence. The [structured findings](product-audit-2026-09-07.json) contain reproduction steps, proposed changes and acceptance criteria for every item. Nothing in this review is a claim that those repairs have been implemented.

## What was tested

The browser pass used the real built React app and real local Worker/Durable Object, with fresh persistence and separate browser origins for commissioner Brandon, player/captain Evan, unclaimed TV and late guest Khoa. It did not use a mocked client snapshot. The existing staging build assets were served locally; the Worker ran from the current working tree. Player layout was checked at 390×844; host and TV screens were inspected at 1280×720. This is an isolated rehearsal of the current implementation, not a claim of testing the Cloudflare deployment/network itself.

Three independent commissioner connections, a player and an unclaimed TV were also exercised against a **second** disposable Worker. Twenty-seven scenarios ran both against the actual action logic and real WebSockets. The authority serialized simultaneous actions and every connected role converged after each step. Six scenarios intentionally reproduced defects; the checks asserted those observed defects rather than counting them as functional passes. The other 21 scenarios matched their expected behavior. An additional deterministic rehearsal covered every built-in event family through official results.

The two environments used distinct storage and ports. Neither the user's existing local tournament on 5173 nor staging/production game data was reset, claimed, advanced or edited. No staging deployment was made. Application source was left unchanged during this review; additions are reports, repeatable audit scripts and ignore entries for disposable local storage. Pre-existing working-tree changes belong to the preceding work.

Evidence labels:

- **Browser:** interaction/observation in the real application, through its UI.
- **Network:** real acknowledged WebSocket actions and broadcast snapshots on the isolated authority.
- **Component:** production component rendering or action execution with controlled sample state. This does not prove browser effects, timing or layout.
- **Code:** a source-backed finding or design concern; not presented as a completed device test.

## What to consolidate, patch and redesign

### 1. Repair task completion and recovery

Patch late check-in and Quick Draw before more layout work. A completed state must mean the server accepted it. Retain suspense, draw flashes and chip feedback, but make waiting, retry and failure visible inside the current task. Keep the reaction tap clear and preserve the same captured attempt on network retries.

**Done when:** a late guest can enter, a rejected run cannot masquerade as saved, and players can complete or leave the flow on their phone. Add regression cases for each actual failure, not just happy-path component snapshots.

### 2. Extend the existing safe commissioner contract

Keep three commissioners. The tested contest/draft system already handles them well. Apply reviewed-result revisions, poker session identity and per-player count revisions to the older handlers. Preserve each commissioner's unsaved edits if another commits, and show the new committed value before an overwrite. Make the frozen-board policy uniform.

**Done when:** the stale-form and replacement-table reproductions are rejected without losing data; different-event and different-player work still proceeds concurrently; retries never advance or settle twice. Show who/what last committed if useful, without making a global single-operator lock a prerequisite.

### 3. Use one live event model across existing routes

Home, Bets, event details, the commissioner next action and TV should share current event, contest, lifecycle and committed result. Fix preparation precedence in the shared model before removing TV's independent scans. A future draft is preparation unless intentionally presented. The same event destination should retain the current room matchup and my own partner/next match/crew status.

**Done when:** both preparation orderings, shelving, active play and result entry agree across roles. Finish the draft handoff by taking all open viewers to confirmed teams; reset scroll for a new task state while preserving true Back/card-return context. Do this inside Home / Events / Bets / Weekend, without adding a fifth navigation area.

### 4. Redesign poker's transition, using the existing counter

The counter's direct denominations and acknowledged saves are useful. The shared workflow is the problem: personal counting currently starts everyone's final-count process. Define playing, collecting counts, review/discrepancy and posted results as distinct states, with room and personal status made visible. Decide how a large discrepancy should be explicitly acknowledged rather than treating it as ordinary completion.

In the browser sample, **2,500 of 13,500** still enabled posting and said that chips get miscounted. That is an observed policy/UX decision to revisit, not a newly alleged calculation bug. The audit reconciled the totals before posting. Recount also reconstructed denominations from the saved total rather than restoring the exact previous denomination entry; preserve those inputs if the intended job is checking the physical pile.

**Done when:** one player's count does not remove another's valid play actions; the host sees received/missing counts and discrepancy; players know whether a count is personal or final; TV shows matching phase, out status and official final stacks. Reuse the session/revision contract from workstream 2.

### 5. Make TV a public, complete and recoverable role

Define its public payload, independent of internal persisted state. Give it loading/disconnected states and useful fallback when a show scene becomes stale. Share current-event and result presentation models with the phones, including the difference between an event award and a final poker stack. Show all 13 players, use readable leader ink and retain access to scenes with reduced motion.

**Done when:** public network payloads contain no private ratings; all 13 people can find themselves; the display always tells the truth about current activity, final stacks and connection freshness. Validate the actual TV/remote and expected unattended duration before choosing fullscreen or keep-awake implementation details.

### 6. Polish context and component boundaries after those contracts

Bring the remaining small targets onto shared controls. Put settled duel details in an existing personal history/card destination. Keep crew labels in shared metadata. Extract TV presentation, poker workflow and Quick Draw lifecycle from the large App composition around the agreed contracts, with regression cases carried into those modules.

**Done when:** removing duplicated selectors/forms actually reduces disagreement and navigation work. Preserve the dark theme, authored voice, full Home leaderboard, direct placement/retraction, separate player-card targets, short event entrances, reveal/replay, pick motion and winner moments. Refactoring should protect these, not flatten the experience.

## Remaining validation before calling the product weekend-ready

This review covers all three requested roles and the breadth of the product with browser, network and component evidence. It does **not** certify every named event on every device. After repairs, repeat the representative journeys with three real phones and the intended TV, including a current-match competitor betting on their own team, late arrival, captain versus non-captain, eliminated player, heat second qualifier, all-counted finale and reconnect mid-write.

Still unverified in this pass: actual iOS/Android installation and camera upload, television/remote and sleep behavior, reduced-motion behavior on intended devices, real Spotify authorization/playback, screen-distance readability at 1080p/4K, network latency/lost-ack fault injection at every write, and browser-based snapshot export/restore. Existing tests cover portions of these contracts, but they are not substitutes for the missing device/integration checks.

An API-prepared poker fixture left an unfinished 8-Ball event in the sample state. That exposed a host next-action inconsistency after the finale, but this report does not count it as a separately verified normal-navigation defect. The independent complete-weekend network rehearsal covered the ordinary finale/champion path.
