# TV role audit · September 7, 2026

## Scope and evidence

Read-only product journey audit of the actual TV implementation in `src/App.jsx`, shared event/contest/director resolvers, client connection handling, spectator entry, and server message permissions. No application files changed. No browser interaction, remote guest data, or persisted tournament writes were used. Findings below are code findings; none are claimed as browser-observed.

The coordinating root task subsequently supplied browser observations. Those are explicitly attributed below and were not performed by this auditor.

Validation used the actual private TV components bundled in memory with esbuild, a throwing transport stub, React server rendering, and `PlayerIdentityProvider`. Private exports were appended only in the in-memory build. Scenarios were prepared with real `applyAction` calls against cloned `EMPTY_STATE`. Nine targeted outputs reproduced the presentation problems below. A separate earlier urgent-crash audit rendered 92 real EventIntro/Reveal combinations without a hero-render exception; the full-App initialization bug was subsequently fixed by the root task.

Focused existing suite: **27 passed** across `m2-director.test.mjs`, `m2-foundations.test.mjs`, `announcement-app.test.mjs`, and `draw-reveal.test.mjs`. Those tests establish director/announcement contracts; they do not cover the TV scene selection and presentation issues reproduced here.

Source line references reflect the working tree at audit time; component/function names provide stable anchors.

## Findings

### TV-01 · P1 · Prepared or shelved events displace actual play

**Evidence:** `TVMode` independently chooses the first unfinished bracket, first unfinished stage and first draft (`App.jsx:4943–4960`). Bracket/stage scans do not exclude shelved events or require a live lifecycle. `liveEv` prefers these preparations over `operationEv` (`5009`). The rendering branch gives any draft precedence over `liveEv` (`5147`).

**Reproduced with accepted actions and actual TV render:**

1. `runDraw` for 8-ball using `defaultQaParticipants`. `state.live` remains false; the shared operation remains Long Putt. TV nevertheless renders **Live bracket** and **Up now**.
2. In that state, `announceEvent(putt)`, then `lockAndStart(putt, current contest references)`. Shared operation is putt/in-progress and `onDeck` is null; TV still renders the prepared bracket.
3. `runDraw(8ball)` followed by `shelve(8ball, true)` still renders Live bracket.
4. Prepare the volleyball draft, then announce/start Long Putt. The shared operation is putt, but actual TV renders the draft's “is on the clock” screen instead of the game.

**Shared extension:** Announce/start putt first, then prepare the future volleyball draft. With monotonically increasing local test timestamps, putt remains in-progress but `resolveWeekendOperation` switches to volley/draw-pending. Its `draft.ts` competes directly with `startedAt` (`shared/core.js:1200–1220`). Merely adopting that resolver unchanged would not fix both orders.

**Before any preparation:** `nextEv` unconditionally excludes `operationEv` (`App.jsx:4968`). When the operation is merely the first scheduled event, this skips that event. Root browser observation: idle TV says **NEXT 8-Ball Doubles** while Home correctly says **FIRST EVENT Long Putt**. Root also independently observed **CHECK-IN / LIVE BRACKET / UP NOW Play-in** after preparing 8-ball while Home stayed on Long Putt. This corroborates the local state/render reproductions above.

**Root browser confirmation after play starts:** After Long Putt was locked and started, the GM offered Enter result, Events showed In progress, and the player's Bets screen showed Long Putt locked. Once the TV intro ended, TV still displayed **8-Ball / LIVE BRACKET / UP NOW Play-in**. This confirms the wrong-event selection in the real browser, independently of the local component reproduction.

**Recommendation:** Define active-play precedence in the shared operation resolver: frozen/finale, actual current contest/play, then intentional preparation. Have TV consume that selection rather than scanning domain objects again. Explicitly exclude shelved and completed events. A preparation preview should be a separately selected presentation, not implied by the existence of a bracket or draft.

**Acceptance:** Both preparation orders and shelved preparations leave the actual playing event primary. Preparing a draw alone never labels it live or Up now.

Before play, TV Next must name the first unplayed event rather than the event after it.

### TV-02 · P1 · TV cannot distinguish current data from loading or stale data

**Evidence:** TV composition passes no `ready`, `connected` or freshness information (`App.jsx:1279–1295`). The phone header's reconnect status (`src/ui/AppChrome.jsx:14`) and phone loading overlay are bypassed. Client `ws.onclose` preserves the snapshot and sets `connected=false` (`src/lib/client.js:103`). `TVPoker` and the ticker continue using `Date.now()` intervals (`App.jsx:4643`, `4975`).

**Condition:** Open `/tv` before the first snapshot, or disconnect a loaded TV while another device records results, changes the poker level, or posts counts. TV can show initial/stale standings and a continuously advancing local clock without saying updates stopped.

**Recommendation:** Give TV explicit initial-loading and disconnected states, retain useful last-known data with a conspicuous stale-data label, and show when it was last updated. Reconnection should refresh automatically. A locally derived clock can continue, but must be labelled as disconnected so it is not mistaken for confirmation of current server state.

### TV-03 · P1 · Unclaimed spectators receive data promised as private

**Evidence:** `/ws` accepts an upgrade without an identity check (`worker/tournament.js:114–120`). `hello` sends `state:this.state` before claim/authentication (`612–616`), and `broadcastState` sends the same complete state to every socket (`707–712`). `EMPTY_STATE` includes `seeds` and full `profiles` (`shared/core.js:378`). Check-in labels ratings private and says they are only used to make fair teams (`Onboarding.jsx:104`).

**Condition:** A fresh unclaimed TV or other unclaimed client receives the snapshot, including every player's ratings and full profile fields. The TV UI does not render the private fields; hiding them in JSX does not change the received payload. This is an existing architectural issue, not introduced by the latest draw fix. No remote payload was fetched for this audit.

**Recommendation:** Create a public snapshot projection for spectators and shared TV displays. Deliver private ratings/profile answers only through the appropriate own-player/GM route. Keep server-authoritative team calculation using private values without distributing those values to spectators. Specify and test the role contract before calling those fields private.

### TV-04 · P2 · Main standings leader is difficult to read

**Evidence:** The ambient leader card uses `background:GOLD_GRAD` and `color:var(--ink)` for rank, name and balance (`App.jsx:5292–5310`). `GOLD_GRAD` is `var(--sun)` (`src/ui/theme.js:6`). Current tokens are bone `#f2eddf` and yellow `#e4d477` (`experience.css:11–13`). Their computed luminance contrast is **1.28:1**.

**Condition:** Any non-tied ambient standings board promotes the leader onto this surface. The most important score becomes the lowest-contrast score. TVMiniBoard already uses dark `--ink0` on the same yellow treatment.

**Recommendation:** Use the existing yellow-surface ink token consistently for the main leader card. Verify names, scores and subtext in an actual 720p/1080p TV browser.

### TV-05 · P2 · Poker presentation confuses old balances, counting and final payout

**Evidence and reproductions:**

- `TVPoker` labels its rail Standings and feeds it `computeStandings`, which intentionally does not apply poker counts until final posting (`App.jsx:4721`, `shared/core.js:770–820`). The out-player mapping merely copies an object; it changes no values or styling. After real `pokerSetup`, `pokerStart` and `pokerBust(Brandon)` actions, Brandon still appears with 1,000 in that rail. Dim avatars under Out are separate from those rows.
- Count submissions set `poker.counts` and result-entry metadata, but TVPoker continues the same clock/standings presentation. It supplies no received/missing count progress.
- After real accepted counts and `pokerResult`, a directed winner scene with a 2,000-chip winner renders **+0 each** and no 2,000 value. `TVDirectedScene` always reads `AWARDS[scene.event.value] || 0` (`App.jsx:4919–4927`); poker has no event-award value. The ambient latest-result branch already handles `res.stacks` correctly (`5247–5250`).

**Recommendation:** Label pre-result values as starting chips, mark busted rows directly, and add a counting phase when official count collection begins. Consolidate winner result presentation so both ambient and directed scenes choose between event awards and final poker stacks from the same derived model.

### TV-06 · P2 · Directed standings omit five players without explanation

**Evidence:** `TVDirectedStandings` renders `standings.slice(0, 8)` (`App.jsx:4820`). It is used for explicit standings scenes and the standings step after a winner. Actual SSR renders 8 of the 13 roster names. There is no page control, remaining-player count, or “Top 8” qualification.

**Condition:** A host advances a winner scene to Standings updated. The five omitted players cannot locate their updated result until a different scene becomes active.

**Recommendation:** Present all 13 in the same two-column board model used by ambient TV, or page through everyone with explicit page state. Do not silently truncate a full-standings surface.

### TV-07 · P2 · A stale scene replaces useful information until a host intervenes

**Evidence:** `resolveShowScene` correctly flags a corrected result revision. `TVMode` gives any returned scene first priority, and `TVDirectedScene` replaces the body with Scene unavailable (`App.jsx:4839–4854`, `5140`). A real rendered stale result scene shows that failure page; the shared director correctly offers `clear-scene`.

**Condition:** A result is corrected while its winner scene is active, an event is removed/shelved, or a client encounters an unsupported scene version. The TV does not recover to live standings or the actual contest on its own. The host recovery controls exist on another device, but viewers lose the useful display meanwhile.

**Recommendation:** Show the ambient/current scene with a small unavailable-scene notice while preserving the host's Clear/Retry controls. Treat presentation failure as a fallback condition instead of replacing the tournament display.

### TV-08 · P2 · Reduced motion removes ambient information access

**Evidence:** `TVMode` starts on the board, then refuses to start its scene interval when `prefersReducedMotion()` is true (`App.jsx:5058–5065`). Scene indicators are noninteractive divs (`5348–5353`); there is no other scene selection on TV. Global reduced-motion CSS also stops the marquee (`shell.css:192–194`).

**Condition:** A TV/browser has reduced motion enabled. With no active game, QR/check-in, Next up, Latest result and the open-wager overview never become the primary scene. Long ticker content is static inside an overflow-hidden container.

**Recommendation:** Preserve scene changes without animated transitions, or provide a visible scene selector/paging control. Reduced motion should affect movement, not availability of information.

### TV-09 · P3 · TV exit and unattended-use affordances are incomplete

**Evidence:** Exit is a 40×40 button with only `✕` as its name (`App.jsx:5111–5114`), below the project's 44px control floor. It has no descriptive aria-label. TV entered by `/tv` remains on that URL after `setTv(false)`. There is no fullscreen/wake-lock handling in the inspected TV path.

**Recommendation:** Label the control Exit TV and use a 44px target. Decide whether route entry should be reflected on exit. Verify actual television/remotes and sleep behavior before adding fullscreen or keep-awake controls; absence of a Wake Lock API call alone does not prove the deployed device sleeps.

### TV-10 · P2 · Phone draw and TV disagree about the assigned event role

**Evidence:** Saved role key `sit-out` intentionally maps to **Event host / Host** through `overflowRoleMeta` (`shared/core.js:163–169`). EventCrewCard and the TV crew ticker use that metadata. Phone DrawAnnouncement instead formats the storage key directly with `role.role.replaceAll("-", " ")` (`src/features/weekend/EventAnnouncement.jsx:90`). Other roles also lose their intended labels: referee becomes “referee” rather than Event official, and on-deck loses the lead assignment.

**Condition:** The same saved draw appears on phones and TV. Root browser observation: Evan is shown as “sit out” in the phone reveal while the event sheet and TV correctly identify Host / Event host. This contradicts the operational assignment rather than merely changing typography.

**Recommendation:** Reuse `overflowRoleMeta(role).label` or its short label in every reveal. Keep storage keys stable and centralize visible role wording; do not reinterpret a compatible legacy key as the guest's instruction.

## Consolidation priorities

1. **One scene selection model.** Correct shared active-play precedence, then remove TV's separate first-bracket/first-stage/first-draft priority rules. Consume the current event, current contest, lifecycle, result and connection status together.
2. **One public display contract.** Explicit public snapshot data, shared player identity, and complete standings data. Keep private guest answers off spectator devices.
3. **One result presentation model.** Distinguish event award, poker final stack and champion; reuse it in ambient and directed scenes. Keep all 13 participants accessible.
4. **Recover to useful content.** Initial loading, disconnection, unsupported/stale scenes, reduced motion and render exceptions should each have a defined display and exit path.

These recommendations do not require new host winner forms, additional game-start steps, automatic audio, or changes to settlement contracts.

## Safe behavior confirmed by source and local checks

- TV is read-only at the interaction surface; winner selection and scene commands remain host controls.
- Current contest wagers and payouts use shared resolvers rather than a TV-specific settlement calculation.
- Official scene writes are GM/capability guarded, retry-safe, and independent of audio; existing focused tests passed.
- Directed scenes reconstruct from official references after reconnect and correctly detect stale revisions.
- Poker final counts remain authoritative; the errors above are presentation errors, not changes to chip settlement.
- Root's announcement initialization fix has actual full-App regression coverage. This audit found no exception in the separately rendered game moments/reveals.
